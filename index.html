An asset register your compliance evidence can rely on.

AssetPulse is a self-hosted inventory and monthly compliance platform. It combines a Flask API, a React dashboard, an Excel import pipeline, role-based access, TOTP MFA, audit logging, and a packaging path for offline Linux hosts. This page records what was built, how it works, what was verified, and what the system does not claim.

01

Context

The system of record is often a spreadsheet. An endpoint list is exported from an MDM, merged with a server list, mailed to a compliance owner, and checked once a month. The file is useful for a week and stale by the next review.

Inventory drifts

The same host can appear twice under different names, addresses, or casing. Decommissioned machines stay in the list because removing them is somebody else’s task.

Evidence is manual

A monthly check depends on someone remembering which tool covers which address, then copying the result back into the sheet without a record of who changed it.

Access is coarse

A shared workbook cannot enforce who may delete an asset, unlock an account, or see the audit trail. Every collaborator can do everything.

AssetPulse’s goal was narrower than an MDM, a vulnerability scanner, or a SIEM. Keep a reliable register, make messy imports survivable, and persist the result of a monthly compliance check onto the asset record with an audit trail. That narrowness is the design.

What was built

The product is a single-organization web application. The table below is the functional inventory; the following sections explain the parts that carry the most engineering weight.

One register, one organization

AssetPulse is not a multi-tenant SaaS. The deployment model assumes one organization controls the server, the database, and the license. That assumption simplifies the authorization model and is stated here so it is not mistaken for a missing feature.

03

Architecture

The browser never talks to the database directly. A React single-page application is served by Nginx, calls the Flask API over HTTPS, and receives JSON. The API owns authentication, authorization, validation, the import transaction, the compliance calculation, and the audit write. SQLAlchemy is the only path to the store.

Why this shape

  • Server-side validation is the boundary. The import wizard can suggest and override mappings, but the API re-validates every row before commit.
  • Compliance is calculated where the data lives. The engine runs against the database, not against a browser copy, so the write-back is atomic with the result.
  • Packaging is part of the architecture. The same application is shipped as containers, a standalone binary, or a serverless function; each path has different constraints.
04

Import pipeline

Imports are treated as a reviewable transaction, not a file upload that writes rows immediately. The pipeline is deliberately split so a validation failure does not become a partial write, and so the operator sees duplicates before they become permanent.

  1. 01 / PARSE

    Read

    Workbook rows are read and returned as raw values with a suggested header mapping.

  2. 02 / MAP

    Map

    Known headers are matched; the operator can override any column, including endpoint type and OS version.

  3. 03 / VALIDATE

    Check

    Addresses are normalized, categories resolved, and duplicates detected per row.

  4. 04 / REVIEW

    Review

    Duplicates are surfaced first. A confirmation is required before non-duplicate rows are committed.

  5. 05 / COMMIT

    Write

    Assets are inserted or updated; tag edits and import actions are recorded in the audit log.

What the edge cases taught

Real spreadsheets do not arrive clean. Three changes came directly from import failures: extract the primary address from a multi-IP cell, create unknown categories during validation instead of rejecting the batch, and make duplicate review an explicit step rather than a silent merge.

Address normalization

A cell such as 10.1.100.28, 10.81.0.28 is common in exports that join management and production networks. The normalizer extracts and validates the first address as the primary IP instead of rejecting the row. The original cell is not silently discarded from the register; the operator can still see the source workbook.

Duplicate handling

The importer does not guess which of two similar rows is canonical. It flags duplicates, switches the wizard to the Duplicates tab, and asks for confirmation before adding the remaining assets. Updating an existing asset is a deliberate choice, not an automatic side effect.

05

Compliance loop

Compliance is a monthly checkpoint, not a live scanner. The value of the module is that the result is attached to the asset record and can be defended later.

  1. 01
    Register the tool

    The compliance owner records the tool and the address range it is expected to cover.

  2. 02
    Run the check

    The engine compares inventory records to the registered tool using shared IP-matching logic.

  3. 03
    Write back the result

    Last status, tool, and check date are persisted on the asset, so the register carries the evidence.

  4. 04
    Record the action

    The check and the write-back are recorded in the audit trail with the acting user and timestamp.

Scope boundary

A compliant status means the last run matched the asset to a registered tool. It is not continuous monitoring, it does not prove the tool is healthy, and it does not replace the tool’s own console. The module records a checkpoint; it does not create one.

06

Security model

The controls below are implemented in the reviewed source. The boundary column is as important as the control: it states what the mechanism does not cover, so an operator does not mistake an application feature for an assurance.

Security controls and their stated boundaries.
Control Implementation Boundary
Authentication Signed JWT tokens containing user ID and role; 24-hour expiry; a 401 forces the client to clear state. Token lifetime is fixed; no refresh-token rotation is described. The signing key comes from JWT_SECRET_KEY, with a development fallback that must be replaced.
Bootstrap First run creates admin with password admin and full permissions; later starts re-assert those permissions. Development bootstrap. Change the password before exposure; no forced first-login rotation is shown.
Idle session Frontend activity listeners expire the session after a configurable window (default 15 minutes). Enforced in the client; it is not a server-side absolute session cap.
MFA TOTP setup, verification, and disable flows per user, plus a mfa_required policy flag. The login check applies when the flag is on or the user enabled MFA, provided a TOTP secret exists; the flag does not enroll an account by itself.
Authorization admin and user roles, plus granular can_delete_assets and can_unlock_accounts flags. Two broad roles and two flags; there is no per-asset ACL.
Brute force Failed attempts are counted; five failures by default lock the account for 15 minutes. Both thresholds are configurable, and an admin can unlock it. Lockout state lives in the user record; it is not a network-level rate limit.
Password policy Optional HIBP k-anonymity check (hibp_enabled) with a fallback when the host has no internet access. Disabled by default. Offline deployments log a warning and allow the flow rather than block operations.
Licensing RS256 JWT verified at startup; on-premise instances exit on failure. Skipped when VERCEL=1. An operational gate, not a security boundary against a modified build.
Audit Append-only event records for critical actions. Application-level append-only; not WORM storage or a remote audit sink.
Secrets Environment variables; .env.example ships with placeholders. Operators must replace defaults; no secrets-manager integration is included.
07

Deployment

Deployment is treated as three operating models, not one script with flags. The constraints that matter are connectivity, update path, and who controls the host.

Connected / Docker GitOps on a Linux host

Clone, set .env, run deploy/deploy.sh. The stack builds PostgreSQL, the Flask backend, and the Nginx front end, then serves on port 8443.

Air-gapped Images as a transferable bundle

Build on a connected runner, docker save the images, transfer the archive, docker load on the isolated host, then start the same Compose file.

Cloud Vercel + managed PostgreSQL

Static frontend, Flask serverless function, and a managed Postgres connection. Useful as a reference deployment; not a claim of production scale.

Packaging notes that mattered

  • PyInstaller and Waitress. When FLASK_ENV=production is set (the systemd unit does this), the backend binary serves through Waitress on port 5000 instead of Flask’s development server. Hidden imports for psycopg2 and waitress are bundled.
  • Nginx DNS resolution. A backend restart could take the proxy down. frontend-react/nginx.conf uses Docker’s internal resolver with a 30-second validity window, so the upstream is re-resolved instead of cached forever.
  • GLIBC compatibility. A mismatch produced GLIBC_2.38 not found. Builder and runtime stages are pinned to python:3.12-slim to keep the binary and the base image aligned.
  • Database migration. Moving from the cloud deployment to an on-premise host uses an export, a transfer, and an import script that skips existing rows with ON CONFLICT DO NOTHING.
08

Findings

These are engineering findings from building and operating the system, not security audit results. Each one changed the implementation.

Multi-address cells failed validation

SymptomRows with two addresses in one cell were rejected as “Invalid IP format”.

ResolutionExtract and validate the first address as the primary IP; keep the source row visible rather than discarding it.

Unknown categories blocked the batch

SymptomA new label such as Database failed validation and stopped the import.

ResolutionCreate unrecognized categories during validation, then commit the batch.

Duplicates were ambiguous

SymptomSimilar rows could be merged or added without the operator seeing the decision.

ResolutionAuto-focus the Duplicates tab and require an explicit confirmation before committing non-duplicate rows.

New fields required a safe migration

SymptomEndpoint type, OS version, and tags were not in the original asset table.

ResolutionOn startup, inspect the asset table and add missing columns inline, preserving existing test data; extend the audit log to tag edits.

The packaged binary exited immediately

SymptomThe PyInstaller build started and stopped; the container had no live process.

ResolutionWrap the Flask app in Waitress on port 5000 and bundle the required hidden imports.

Nginx died when the backend restarted

SymptomA proxy upstream cached at startup made the front end unavailable during a backend restart.

ResolutionUse Docker’s internal DNS resolver with a 30-second validity window so the upstream is refreshed.

Base-image mismatch broke the binary

SymptomThe runtime reported GLIBC_2.38 not found.

ResolutionPin builder and runtime stages to python:3.12-slim.

Offline password checks need a fallback

SymptomHIBP lookups are impossible on an air-gapped host.

ResolutionLog a warning and allow the flow rather than blocking authentication; document the reduced assurance.

09

Scope & limits

In scope

  • Single-organization asset register
  • Asset CRUD, lifecycle, categories, tags
  • Excel import with mapping and duplicate review
  • Monthly compliance write-back
  • JWT authentication, TOTP, RBAC, audit
  • Licensed Docker, air-gapped, and cloud paths

Not claimed

  • Agent-based discovery or MDM
  • Vulnerability scanning or patch management
  • Continuous compliance monitoring
  • SSO, SCIM, or multi-tenancy
  • SIEM integration or WORM audit storage
  • External certification or penetration test

Limitations

  1. Evidence freshness depends on the last run. A green status is only as current as the compliance check that produced it.
  2. Duplicate resolution is human-reviewed. The importer flags; it does not merge identities automatically.
  3. Audit immutability is application-level. A database administrator can still alter rows directly.
  4. SQLite is the development default. PostgreSQL is the Docker path; the two are not interchangeable at scale.
  5. No independent assurance. The repository contains no external penetration-test report or certification evidence.
  6. License checks assume an untampered build. They are a commercial gate, not a defense against a modified binary.
  7. The public cloud target is a reference deployment. It is not presented as evidence of production capacity or uptime.

What this evidence proves

  • The import, compliance, access-control, audit, and licensing paths exist in code and are connected to the data model.
  • Three real spreadsheet shapes were used during development, and the edge cases they exposed changed the implementation.
  • Two deployment models are documented and packaged: Docker and an offline image bundle.

What it does not prove

  • That the system has been independently reviewed, certified, or tested against a formal threat model.
  • That it scales to a given inventory size or request rate.
  • That the importer handles every possible workbook layout or encoding.
  • That the public cloud target is the production application; it is the marketing surface.

11

Summary

AssetPulse is a narrow system with a clear job: keep an asset register clean enough that a monthly compliance result can be attached to it and defended later.

The build is complete across inventory, import, compliance, access control, audit, licensing, and two deployment models. The interesting engineering is at the edges: messy spreadsheets, restarts, image packaging, and the difference between recording a checkpoint and claiming continuous assurance.

The next evidence gaps are a repeatable test suite and an independent review. Until those exist, the correct description is “implemented and documented”, not “verified by a third party”.
